# Workflow Policy

## 1. 原則的な状態遷移

DRAFT / RETURNED
→ SUBMITTED
→ FIRST_APPROVED / SECOND_APPROVED / TRIP_APPROVED / FINAL_APPROVED / REJECTED / RETURNED
→ WITHDRAWN (CANCELLED)

業務種別に応じて多段階承認および独立した復命書承認を許容する。

## 2. ワークフローサイクル分離（Workflow Cycle Separation）

1. **再処理の独立世代化**: `RETURNED` 状態からの再申請（Resubmit）、再承認、再審査等の再処理は、過去状態の巻き戻しではなく新世代の `approval_cycle` を発行して独立記録する。
2. **履歴の不可逆的保持（Historical Record Immutability）**: 再提出・再承認時に過去サイクルの承認・差戻し・コメント・印影・日時の全ステップ履歴を削除・上書きしてはならない。
3. **完全追跡性**: 起案から最終決裁に至るすべての差し戻し理由、修正内容、各世代の判断経緯を完全に監査可能とする。

## 3. ドメインライフサイクル分離（Domain Lifecycle Isolation）

1. **出張命令と復命書の独立性**: `TRIP_APPROVED` 後の復命書が差戻された場合（`REPORT_RETURNED`）、出張命令自体の承認状態・法的効力は維持されたまま、復命書ドメインのみ `REPORT_SUBMITTED` へ再提出される。
2. **親ドメイン保護**: 申請と報告、命令と復命、承認と月次確定など、法的・業務的な成立時点が異なるドメインにおいて、子ドメインの差戻し・取消によって成立済みの親ドメインを未承認へ巻き戻してはならない。

## 4. サーバー所有属性の保護（Server-Owned Immutable Identity）

1. **本質属性の変更禁止**: 再提出や更新時において、申請種別（`typeId`）、申請対象者（`targetEmployeeId`）、制度バージョン、承認ルート等の本質的属性をClient送信値のみによって変更することは禁止する（変更が必要な場合は取下げの上で新規起案）。
2. **Server検証の強制**: Clientから送信された属性値はServer側の既存確定データと照合検証し、不整合時は即座に拒絶する。

## 5. 永続化整合性境界と冪等性（Persistent State Consistency & Idempotency）

1. **不可分な状態更新**: 申請・再申請・承認・差戻し・却下・取消等のワークフロー状態変更は、本体更新・ステップ追加・関連テーブル更新・AuditLog記録を含め、単一の整合性境界（All-or-Nothing）で実行する。
2. **再実行時の二重計上防止**: 通信リトライや再提出によって、残日数・残時間の重複控除や出勤簿集計の二重計上を発生させてはならない。

## 6. 禁止事項

- APPROVEDされていない申請の正式反映
- REJECTEDまたはFINAL_APPROVEDからの再提出・直接遷移
- 権限のない承認・操作
- 自己承認（本人および代理起案者による自己承認）
- 過去の承認ステップ・コメント・印影の物理削除または上書き
- 承認済み親ドメインの不当な巻き戻し
- Client改ざんによる申請種別・対象者・承認ルートのすり替え

## 7. Policy-Driven 承認ルート管理ポリシー（Policy Governance Rules）

1. **N:M 構造による共通ポリシー再利用**:
   - 承認ポリシーは単一の申請種別にハードコードされず、中間テーブル（`workflow_policy_application_types`）を通じて複数申請種別へ安全に共有される。
2. **ACTIVE バージョンの不変性と Atomic な世代交代**:
   - `ACTIVE` バージョンの業務定義（ステップ構成、セレクター、優先度等）の直接変更は厳格に禁止する。
   - ルートや役職割当の改定時は新規ドラフトバージョン（v(N+1)）を作成・検証した上で、単一トランザクションにより旧バージョンを `INACTIVE` 退役させて新バージョンを `ACTIVE` 化する。
3. **役職（Position）と権限（Role）の分離**:
   - 承認ルート上の単一責任者（教頭、校長等）は `POSITION` セレクターにより決定論的に単一ユーザーを特定する。
   - 業務認可（教員、事務室等）は `ROLE` セレクターにより判定する。
4. **Fail-Closed 原則の徹底**:
   - Policy Version 未解決（0件）、複数重複解決（同順位競合）、役職担当者不在、担当者重複、最終決裁ステップ数不正（0件または複数件）が発生した場合は、一切の暗黙フォールバックを行わず即座に Fail-Closed 遮断する。
