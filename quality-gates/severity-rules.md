# Severity Rules

問題の重大性（Severity）は以下の客観的基準に基づき分類する。AIはテスト通過やGO判定のために恣意的に格下げしてはならない。

---

## P0 Critical（本番投入絶対不可・即時NO-GO）

業務・法的・セキュリティ・データ整合性に致命的な影響を与える問題。

例：
- **監査・業務履歴の破壊/消失**: 過去の承認ステップ・差戻し理由・印影・日時の物理削除または上書き
- **法令・服務上の状態破壊**: 成立済みの親ドメイン（出張命令承認等）が子ドメイン差戻しで破壊される問題
- **残数・財務の二重計上**: 年休残日数・残時間の二重減算・二重計上
- **非Atomicな複合更新**: 複数DB更新で部分コミットが発生しDB不整合を残す問題
- **Client改ざんによる制度回避**: Client送信値のみで申請種別・対象者・承認ルートが変更可能
- **正式帳票・出勤簿への誤記・誤反映**: 未承認データの反映、制度計算の重大な不整合
- **自己承認・権限突破**: 本人による決裁、RBAC回避
- **Fail-Closed違反**: 未知状態（UNKNOWN）の推測による正常終了、Core Impact = UNKNOWN のままの実装進行
- **Quality Baseline改ざん・無承認緩和**: PO承認なきInvariant緩和・削除、Golden Case期待値改ざん、Gate免除、Quality Coverage Baselineの無承認低下
- **未承認 Core Semantic Change**: PO/QA承認なきLayer A3の改変、Core Regression Shieldの破壊・スキップ
- **Stage 境界侵害・権威の無承認昇格**: Stage 1（PILOT READY）を根拠とした無承認の本番権威昇格（Stage 3）、受動的時間（Time）や測定パラメータの品質合否判定基準（Quality Threshold）への不正すり替え

---

## P1 High（重大事故・本番投入不可）

実務上の重大な不具合、または将来的にP0へ発展する構造的欠陥。

例：
- **Authoritative Domain Logic 重複**: 同一制度判定・条例計算ロジックの複数箇所への独自再実装
- **永続化整合性境界の不明瞭さ**: トランザクション境界が明示されておらずロールバック検証が欠落
- **ワークフロー世代（Cycle）追跡不足**: 差戻し後の再申請で世代番号が管理されていない
- **Audit証跡不足**: 重要操作の変更前・変更後ステータスやactorが記録されない
- **DB外副作用の混在**: PDF生成や外部通知がSQLiteトランザクション内に無理に抱え込まれている設計

---

## P2 Medium（限定的条件での不具合）

通常業務フローへの影響が限定的であり、回避策が存在する問題。

例：
- エラーメッセージの不親切さ
- 限定的な表示不整合（正式データ自体は正常）
- 軽微なテスト可読性・構造改善事項

---

## P3 Low（軽微な改善）

コードスタイル、コメントの補足、将来的なリファクタリング提案。

コードの美しさだけを理由にP0/P1と判定してはならない。
