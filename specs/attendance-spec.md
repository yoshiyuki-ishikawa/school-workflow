# Attendance Specification

## 1. 生成フローと共通ロジックの利用

出勤簿は、承認済みかつ有効な正式データ（Canonical Facts）からServer側で決定論的に生成する。独自に条例ルールを再実装してはならない。

基本処理フロー：
1. 対象教職員・勤務パターンの取得
2. 暦日情報（平日・休日・週休日・代休日）の取得
3. 確定済み服務データ（承認済み申請・出張命令等）の取得
4. 共通 Authoritative Domain Logic による服務状態・集計判定（Canonical Facts解決）
5. 排他服務の競合判定（解決不能時はFail-Closed）
6. 出勤簿表示コード・記号の決定
7. 集計カテゴリへの算入処理
8. 出勤簿DTOの生成

## 2. 厳格な規約

1. **Client指定の禁止**: Clientから出勤簿表示コードや集計値を直接指定・上書きすることはできない。
2. **ライフサイクル整合性**: 出張命令が承認済（`TRIP_APPROVED`）であれば、復命書が差戻し中であっても出勤簿上の出張服務事実は正しく反映される。
3. **Canonical Nameと様式番号の分離 (INV-026)**: 出勤簿のCanonical Domain Nameは「出勤簿」、Canonical Keyは `ATTENDANCE_BOOK` とする。「第○号様式」「別記様式第○号」等の自治体固有帳票番号を固定識別子や固定文言として使用しない。学校組織情報からは自治体固有の規程名称設定を撤去し、将来必要な場合はPolicy/Jurisdictionメタデータ層で管理する。
